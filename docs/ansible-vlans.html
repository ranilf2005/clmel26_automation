Ansible VLAN Task

Configure VLANs as code with Ansible — the pipeline catches a wrong VLAN or interface in test/dev before anything reaches production.

How this fits the lab

The earlier steps used a GitLab pipeline with pyATS. This task adds an Ansible workflow driven by GitHub Actions — because this repository is hosted on GitHub. Same NetDevOps idea, second tool-chain: describe intent in YAML, let CI validate it, and gate the deploy on success.

The scenario

You describe the VLANs and access ports you want in a small YAML file and git push. GitHub Actions runs a validate job (the test/dev environment). If you typed a wrong VLAN id or interface name, the job FAILS with a clear, detailed message and nothing is deployed. You fix the file, push again, and once every check is green the pipeline lets you promote to production behind a manual-approval gate.

Step 1 — Describe your VLANs

Edit ansible/vars/vlans.yml. This is the only file most attendees touch. Each VLAN has an id, a name, and one or more access interfaces.

ansible/vars/vlans.yml
vlans:
  - id: 10
    name: USERS
    interfaces:
      - GigabitEthernet0/1
  - id: 20
    name: VOICE
    interfaces:
      - GigabitEthernet0/2
  - id: 30
    name: MGMT
    interfaces:
      - GigabitEthernet0/3

The test/dev job enforces these rules before any device is touched:

FieldRuleValid example
idWhole number 1–4094; must not use the reserved range 1002–1005; must be unique.10
name1–32 characters: letters, numbers, _ or - (no spaces).USERS
interfacesMust match GigabitEthernet<slot>/<port>.GigabitEthernet0/1

Step 2 — The test/dev gate

validate_vlans.yml runs on localhost with connection: local — pure static checks, no router login. It runs first on the lab runner (198.18.1.4) and validates your intent before anything can reach the network.

ansible/playbooks/validate_vlans.yml
---
- name: "TEST/DEV - validate VLAN and interface intent"
  hosts: localhost
  connection: local
  gather_facts: false
  vars_files:
    - ../vars/vlans.yml
  tasks:
    - name: "VLAN id must be a whole number in the range 1-4094"
      ansible.builtin.assert:
        that:
          - (item.id | string) is match('^[0-9]+$')
          - (item.id | int) >= 1
          - (item.id | int) <= 4094
          - not ((item.id | int) >= 1002 and (item.id | int) <= 1005)
        fail_msg: >-
          INVALID VLAN id '{{ item.id }}' (name '{{ item.name | default("?") }}').
          VLAN ids must be a whole number 1-4094 and must not use the reserved
          range 1002-1005. Fix vars/vlans.yml and push again.
        quiet: true
      loop: "{{ vlans }}"
      loop_control:
        label: "vlan {{ item.id | default('?') }}"

    - name: "VLAN name must be 1-32 chars with no spaces"
      ansible.builtin.assert:
        that:
          - item.name is defined
          - (item.name | string) | length > 0
          - (item.name | string) | length <= 32
          - item.name is match('^[A-Za-z0-9_-]+$')
        fail_msg: "INVALID VLAN name for VLAN id {{ item.id | default('?') }}."
        quiet: true
      loop: "{{ vlans }}"

    - name: "Interface must match GigabitEthernet<slot>/<port>"
      ansible.builtin.assert:
        that:
          - item.1 is match('^GigabitEthernet[0-9]+/[0-9]+$')
        fail_msg: >-
          INVALID interface '{{ item.1 }}' on VLAN {{ item.0.id }}. Interfaces
          must look like GigabitEthernet<slot>/<port> (for example
          GigabitEthernet0/1). Check for typos and push again.
        quiet: true
      loop: "{{ vlans | subelements('interfaces') }}"
      loop_control:
        label: "{{ item.1 }}"
Why asserts, not a device

Catching a bad VLAN id or a mistyped interface is a schema problem, not a network one. Validating it with assert means the mistake is caught in seconds, for free, and can never reach a router.

The deploy never runs

The deploy job declares needs: validate. Because validate failed, GitHub Actions skips deploy entirely — the routers in production are never contacted. This is the whole point: mistakes stop in test/dev.

Step 5 — Promote to production

Once validate is green, the deploy job becomes eligible. It is gated three ways so a human stays in control:

  1. needs: validate

    Deploy cannot start until every test/dev check passes.

  2. Branch guard

    if: github.ref == 'refs/heads/main' — only the main branch can deploy; pull requests never do.

  3. Environment approval

    environment: production — add required reviewers so the run pauses for a manual Approve click.

The deploy runs configure_vlans.yml, which turns your YAML into config with the cisco.ios modules and saves it.

ansible/playbooks/configure_vlans.yml
---
- name: "Configure VLANs and access ports from vars/vlans.yml"
  hosts: "{{ target | default('test') }}"
  gather_facts: false
  vars_files:
    - ../vars/vlans.yml
  tasks:
    - name: Build the ios_vlans config list
      ansible.builtin.set_fact:
        vlan_config: "{{ vlan_config | default([]) + [{'vlan_id': item.id, 'name': item.name}] }}"
      loop: "{{ vlans }}"

    - name: Create or update VLANs
      cisco.ios.ios_vlans:
        config: "{{ vlan_config }}"
        state: merged

    - name: Assign access VLANs to interfaces
      cisco.ios.ios_l2_interfaces:
        config:
          - name: "{{ item.1 }}"
            mode: access
            access:
              vlan: "{{ item.0.id }}"
        state: merged
      loop: "{{ vlans | subelements('interfaces') }}"

    - name: Save running-config to startup-config
      cisco.ios.ios_config:
        save_when: modified

Why a lab runner

The routers 198.18.1.6 / 198.18.1.7 are only reachable from inside the pod, so the pipeline runs on the self-hosted runner on the devbox 198.18.1.4 — not a GitHub-hosted runner. Protect the production environment with required reviewers under Settings → Environments so the deploy waits for a manual Approve.

The GitHub Actions pipeline

One workflow ties it together: validate (test/dev) then a gated deploy (production).

.github/workflows/ansible-vlan.yml
name: Ansible VLAN CI/CD

on:
  push:
    paths: ["ansible/**", ".github/workflows/ansible-vlan.yml"]
  pull_request:
    paths: ["ansible/**"]
  workflow_dispatch:

defaults:
  run:
    working-directory: ansible

jobs:
  validate:                      # ---- TEST / DEV ----
    name: "Test / Dev - validate intent"
    runs-on: [self-hosted, clmel]   # lab runner on the devbox 198.18.1.4
    steps:
      - uses: actions/checkout@v4
      - name: Ensure Ansible and linters
        run: |
          python3 -m pip install --user "ansible-core>=2.16" ansible-lint yamllint
          echo "$HOME/.local/bin" >> "$GITHUB_PATH"
          ansible-galaxy collection install -r requirements.yml
      - name: Lint YAML
        run: yamllint .
      - name: Lint playbooks
        run: ansible-lint playbooks/
      - name: Syntax check
        run: ansible-playbook playbooks/configure_vlans.yml --syntax-check
      - name: Validate VLAN and interface intent
        run: ansible-playbook playbooks/validate_vlans.yml

  deploy:                        # ---- PRODUCTION (gated) ----
    name: "Production - apply to routers"
    needs: validate
    if: github.ref == 'refs/heads/main' && github.event_name != 'pull_request'
    runs-on: [self-hosted, clmel]   # devbox 198.18.1.4 -> routers .6/.7
    environment:
      name: production           # add required reviewers = manual approval
      url: https://ranilf2005.github.io/clmel26_automation/
    steps:
      - uses: actions/checkout@v4
      - name: Ensure collections
        run: ansible-galaxy collection install -r requirements.yml
      - name: Deploy VLANs to production
        run: ansible-playbook -i inventory/hosts.yml playbooks/configure_vlans.yml -e target=prod

Try it locally

You can run the exact test/dev gate on the devbox before you ever push.

bash
cd ansible
ansible-galaxy collection install -r requirements.yml

# 1) Static validation - the test/dev gate (no devices needed)
ansible-playbook playbooks/validate_vlans.yml

# 2) Syntax-check the config playbook
ansible-playbook playbooks/configure_vlans.yml --syntax-check

# 3) Dry-run against the test devices (needs CML reachability)
ansible-playbook playbooks/configure_vlans.yml -e target=test --check --diff

# 4) Apply for real (normally done by the gated CI job)
ansible-playbook playbooks/configure_vlans.yml -e target=prod
Secrets in real life

This lab keeps the well-known lab password in group_vars/all.yml for convenience. In production, store credentials with Ansible Vault or GitHub encrypted secrets — never commit plain-text passwords.
