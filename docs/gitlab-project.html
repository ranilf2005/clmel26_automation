Create a New Project in GitLab

Stand up the repository, define the pipeline, and push the automation project.

The devbox includes an instance of GitLab-CE used as your version control system, along with a CI/CD runner that executes pipelines for building, testing, and deploying changes. You create a new project (git repository) to provide an Infrastructure-as-Code approach to network changes: when you push, changes are automatically deployed and tested in your CML lab.

Pipeline flow

  1. Runner pulls the repo

    The GitLab Runner checks out the latest commit.

  2. pyATS tests run

    Ping and static-route checks execute against the CML devices.

  3. Fail → stop

    If tests FAIL, the pipeline stops and nothing is deployed.

  4. Pass → deploy

    If tests PASS, configure_loopback.py applies Loopback300.

  5. Report

    The final pipeline result is shown in GitLab.

Expected results

Case A All tests pass

Pipeline shows SUCCESS and the loopback is configured on both routers.

Case B Any test fails

Pipeline shows FAILED and the loopback is not configured.

Lab attendee tasks

  1. Inspect testbed.yaml and confirm the router details.
  2. Run a pipeline in GitLab.
  3. Observe the pass / fail output in GitLab CI/CD.
  4. If passed, log in to the router and verify the loopback exists.
    • If the loopback exists, the pipeline skips and passes.
    • If not, configure the loopback interfaces with the IP/mask.
  5. If failed, troubleshoot until the tests pass.

    Log in to the Ubuntu PC GUI, or SSH into it at 198.18.1.4 if using the VPN.

  2. Confirm the containers are running

  3. Log in to the GitLab UI

    Open http://198.18.1.4:8929/ and sign in.

  4. Create a new blank project

    In the GitLab UI, create a new blank project and fill in the details for your automation project.

  5. Enable the runner for the project

    In Settings → CI/CD → Runners, ensure the pyats-fast runner is enabled for this project.

Clone and populate the repository

  1. Clone with HTTPS

    Open a terminal on the devbox and clone your new project (use the HTTPS clone URL shown in GitLab).

    bash
    cd /home/cisco/pyats_project/
git clone http://198.18.1.4:8929/root/<your-project>.git
cd <your-project>

  2. Create the project files

    Create the directory structure below. You can create folders and files with mkdir and an editor such as vi or nano.

    project structure
    .gitlab-ci.yml
testbed/testbed.yaml
jobs/smoke_job.py
jobs/configure_loopback.py
jobs/tests/test_ping_routes.py
configs/loopbacks.yaml
    Shortcut

    Your instructor can point you to a copy of all project files instead of typing them by hand. If you get stuck, see the solution files in /home/cisco/clmel.solution/. Every file is also listed on the Project Files page.

  3. Commit your changes

    Stage and commit the files with a message.

    bash
    git add .
git commit -m "add pyATS pipeline and testbed"

  4. Push to start the pipeline

    Push to GitLab, which triggers your new pipeline. Authenticate with username cisco and password C1sco12345.

    bash
    git push

Observe the pipeline

In the GitLab UI, open Build → Pipelines (or navigate to http://198.18.1.4:8929/root/<your-project>/-/pipelines/). Check the status and click into a job to inspect its log.

Expected first run: FAILED

On the first run the test stage typically fails because both routers cannot ping the gateway 192.168.1.1. Click the failed job to view the errors.

  1. Read the failure

    Open the failed pyats_tests job and read the ping failure in the log.

  2. Troubleshoot in CML

    Open CML at http://198.18.1.2/, review the running configuration of the routers, and fix the reason the gateway is unreachable.

  3. Re-trigger the pipeline

    Commit and push the fix from the terminal (repeat the commit / push step) or re-run the pipeline manually from the GitLab UI.

  4. Confirm success

    When tests pass, the deploy_loopback stage runs and applies Loopback300. Verify on each router.

    router#
    show ip interface brief | include Loopback300
show running-config interface Loopback300
Idempotent by design

If Loopback300 already has 2.2.2.2, configure_loopback.py detects it and skips — so re-running the pipeline is safe. See the Appendix.
