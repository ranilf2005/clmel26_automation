Pipeline Run

What a real execution looks like, stage by stage.

Two stages, one gate

The pipeline defines two stages in .gitlab-ci.yml. The deploy stage uses needs: ["pyats_tests"], so it only runs when the test stage succeeds.

sequenceDiagram
    participant Dev as Devbox
    participant GL as GitLab
    participant RN as Runner (pyats-fast)
    participant CML as CML routers
    Dev->>GL: git push
    GL->>RN: start pipeline
    Note over RN: Stage 1 — test
    RN->>CML: pyATS ping 192.168.1.1
    RN->>CML: compare static routes
    alt any test fails
        CML-->>RN: failure
        RN-->>GL: pyats_tests FAILED
        Note over GL: deploy is skipped
    else all tests pass
        CML-->>RN: success
        RN-->>GL: pyats_tests PASSED
        Note over RN: Stage 2 — deploy
        RN->>CML: configure Loopback300 2.2.2.2/32
        CML-->>RN: verified
        RN-->>GL: deploy_loopback PASSED
    end

Stage 1 — pyATS tests

The pyats_tests job runs the smoke job, which executes the reachability and route-consistency test cases.

Example: first run FAILED

pyats_tests — job log
== pyATS version ==
pyATS version : 24.x
== Running smoke job ==
+------------------------------------------------------------------+
|                       Starting testcase PingGateway              |
+------------------------------------------------------------------+
iosv-1      : ping 192.168.1.1 -> Success rate is 0 percent (0/5)
csr1000v-0  : ping 192.168.1.1 -> Success rate is 0 percent (0/5)
FAILED: Ping test failures:
  iosv-1 failed to ping 192.168.1.1
  csr1000v-0 failed to ping 192.168.1.1

Job failed: exit code 1
Why it fails first

The gateway 192.168.1.1 is unreachable until you correct the router configuration in CML. This is intentional — it demonstrates the pipeline stopping before any change reaches the network.

Example: after the fix PASSED

pyats_tests — job log
== Running smoke job ==
PingGateway        : iosv-1     Success rate is 100 percent (5/5)
PingGateway        : csr1000v-0 Success rate is 100 percent (5/5)
PASSED: PingGateway
StaticRoutesEqual  : routes match across devices
PASSED: StaticRoutesEqual

Summary: 2 passed, 0 failed
Job succeeded

Stage 2 — deploy loopback

Once tests pass, the deploy_loopback job runs configure_loopback.py to apply the loopbacks defined in configs/loopbacks.yaml.

deploy_loopback — job log
All tests passed. Deploying loopbacks defined in configs/loopbacks.yaml ...

=== Connecting to iosv-1 ===
[CFG] iosv-1: configuring Loopback300 2.2.2.2 255.255.255.255
[OK]  iosv-1: verified Loopback300 has 2.2.2.2

=== Connecting to csr1000v-0 ===
[CFG] csr1000v-0: configuring Loopback300 2.2.2.2 255.255.255.255
[OK]  csr1000v-0: verified Loopback300 has 2.2.2.2

Pipeline SUCCESS

Verify on the routers

router#
iosv-1# show ip interface brief | include Loopback300
Loopback300            2.2.2.2         YES manual up      up

iosv-1# show running-config interface Loopback300
interface Loopback300
 ip address 2.2.2.2 255.255.255.255
end

SUCCESS

Both stages are green; Loopback300 is present on both routers and saved to the startup config.

FAILED

The test stage is red; the deploy stage never runs and the routers are untouched.

Artifacts

The test job saves pyATS logs as artifacts under logs/<pipeline-id> for 7 days, so you can download and review the full run afterwards.
