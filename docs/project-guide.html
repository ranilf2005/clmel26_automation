1 · What this lab is

This repository is a working example of “network as code.” Instead of an engineer logging into routers by hand, the intended state of the network is written into small text files, committed to Git, and pushed. A CI/CD pipeline then automatically validates the change (lint + schema checks + live network tests) and — only if validation passes — deploys it to the routers.

The lab demonstrates two automation stacks against the same pair of virtual routers:

StackToolingManagesRuns on
Ansible VLAN taskAnsible + cisco.iosVLANs & access portsGitLab CI + GitHub Actions
pyATS / Genie taskspyATS + Genie + UniconReachability tests, static routes, LoopbacksGitLab CI
The one idea

Validate before you touch production. If any test fails, change nothing. Every job in this project is built around that guardrail.

2 · Why CI/CD? Importance & benefits to the company

Traditional network changes are manual, unaudited, and risky: one mistyped VLAN id or interface name can black-hole traffic, changes hit production with no automated test, and there is no consistent record of who changed what or whether it was reviewed.

8 · Pipeline stages & flow

GitLab CI/CD (.gitlab-ci.yml)

git pushroot/clmel26_automation
→
Stage 1 · validatevalidate_intent — yamllint + ansible-lint + syntax + schema asserts
Stage 2 · network_checkping_and_loopback — ping gate → Loopback3
→
Stage 3 · deploydeploy_prod — MANUAL button → apply VLANs (needs validate)
Stop on failschema invalid or network unreachable → nothing changes
  • validate → validate_intent: installs Ansible + linters, then yamllint, ansible-lint, --syntax-check, and validate_vlans.yml. Pure static checks — no device touched.
  • network_check → ping_and_loopback: needs: [] (independent), runs the pyATS ping-gate script.
  • deploy → deploy_prod: needs: ["validate_intent"] and when: manual — a human clicks Deploy; it dry-runs then applies the VLANs.

GitHub Actions (.github/workflows/ansible-vlan.yml)

validate (test/dev) → deploy (prod). deploy requires needs: validate, only runs on main (not PRs), and uses environment: production (add required reviewers for approval). Both jobs run on [self-hosted, clmel].

9 · Failure scenarios — and how to check them

Each scenario shows how to trigger it, what you should see, and where to look. In every case, production is left untouched.

F1 — Invalid VLAN id (out of range)

Trigger

In ansible/vars/vlans.yml set a VLAN id: 5000 (valid range 1–4094), commit & push.

Expected: the validate job fails on the id assertion:

INVALID VLAN id '5000' (name 'VOICE'). VLAN ids must be a whole number
1-4094 and must not use the reserved range 1002-1005. Fix vars/vlans.yml
and push again.

Check: GitLab → CI/CD → Pipelines → the failing validate_intent job log; the deploy stage never starts.

F2 — Invalid VLAN name or interface name

Trigger

Set a VLAN name with a space (VOICE PHONES) or an interface typo (GigabitEth0/1).

Expected: the name assertion (1–32 chars, no spaces) or interface assertion (GigabitEthernet<slot>/<port>) fails with a message naming the offending value. Check: same validate log.

F3 — Duplicate VLAN id

Trigger

Define the same id twice in vars/vlans.yml.

Expected: Duplicate VLAN ids detected …. Check: validate log.

F4 — Network unreachable (ping gate)

Trigger

In configs/loopback3.yaml set ping_target: 198.168.1.1 (unreachable), push.

Expected — ping_and_loopback stops before any config:

======================================================================
STEP 1  Ping pre-check  ->  every router must reach 198.168.1.1
======================================================================
  [FAIL] iosv-1 -> 198.168.1.1: success rate 0%   (Success rate is 0 percent (0/5))
  [FAIL] csr1000v-0 -> 198.168.1.1: success rate 0%   (Success rate is 0 percent (0/5))
======================================================================
PIPELINE FAILED  -  ping pre-check did not pass
======================================================================
One or more routers cannot reach 198.168.1.1, so Loopback3 was
NOT created on ANY device. Fix reachability and re-run the pipeline.

The job exits 1 → the network_check stage is red → no Loopback3 is created. Confirm on the routers: show ip interface brief | include Loopback3.

Verified live

Target 198.168.1.1 returns 0% from both routers (fails); 192.168.1.1 returns 100% (passes).

10 · Working scenarios — and how to check them

W1 — Valid VLANs deploy

With valid VLANs (default USERS/10, VOICE/20, MGMT/30): validate passes → click Deploy on deploy_prod. Verify:

show vlan brief
show running-config interface GigabitEthernet0/1   ! switchport access vlan 10

W2 — Ping passes → Loopback3 created

With ping_target: 192.168.1.1:

STEP 1  Ping pre-check  ->  every router must reach 192.168.1.1
  [PASS] iosv-1 -> 192.168.1.1: success rate 100%   (... 5/5 ...)
  [PASS] csr1000v-0 -> 192.168.1.1: success rate 100%   (... 5/5 ...)
  OK: every router reached 192.168.1.1. Proceeding to Loopback3.
STEP 2  Create Loopback3 on each router (skip if duplicate)
  [CFG ] csr1000v-0: creating Loopback3 3.3.3.1 255.255.255.255
  [OK  ] csr1000v-0: verified Loopback3 has 3.3.3.1
  [CFG ] iosv-1: creating Loopback3 3.3.3.2 255.255.255.255
  [OK  ] iosv-1: verified Loopback3 has 3.3.3.2
SUCCESS  -  ping passed and Loopback3 is in place on all routers

Verify on the routers:

csr1000v-0#  show ip interface brief | include Loopback3     ! Loopback3  3.3.3.1  up  up
iosv-1#      show ip interface brief | include Loopback3     ! Loopback3  3.3.3.2  up  up

W3 — Duplicate Loopback is skipped (idempotent)

Expected

Re-running when Loopback3 already exists prints [SKIP] … already exists (duplicate) (or duplicate IP). The job still succeeds — pipelines are safe to retry.

W4 — pyATS ping/route test passes

pyats run job jobs/smoke_job.py --testbed-file testbed/testbed.yaml — PingGateway passes at 100% to 192.168.1.1; StaticRoutesEqual passes when both routers share the same static routes.

13 · Port it to another server

  1. Copy the repo (or just jobs/, testbed/, configs/, ansible/, and one of .gitlab-ci.yml / .github/workflows/).
  2. Update device details in testbed/testbed.yaml and ansible/inventory/hosts.yml + ansible/group_vars/all.yml. Move secrets to Ansible Vault or CI/CD variables — never commit plain-text passwords in production.
  3. Point the ping target in configs/loopback3.yaml at an address your routers should reach.
  4. Provide a runner. GitLab: register a runner, tag it, set that tag in .gitlab-ci.yml (default.tags); if you don't use the registry image, add a before_script that pip install pyats[full] genie PyYAML. GitHub: register a self-hosted runner with a label and set it in runs-on:.
  5. Re-point the image in .gitlab-ci.yml (default.image) to your pyATS image, or drop it and install deps in before_script.
  6. Render this doc anywhere: project-guide.md renders on GitLab/GitHub/Obsidian; project-guide.html opens standalone in any browser with no dependencies.

Glossary

  • CI/CD — Continuous Integration / Continuous Delivery: automatically test every change and safely deliver it.
  • Runner — the agent that executes pipeline jobs (here: docker-executor containers on the devbox).
  • pyATS / Genie / Unicon — Cisco's Python test/automation framework, its parsing library, and its device-connection library.
  • Testbed — the pyATS device inventory (testbed/testbed.yaml).
  • Idempotent — running a job again produces the same result without creating duplicates.
  • Gate — a stage that blocks progress until a condition is met (tests pass, a human approves).
